## 2. The three views closest to the founding need

**1. Wumpus browser-workbench lineage panel (`traceAddress`), row 16.** It is the only rendered, interactive surface anywhere that answers all four halves of the origin question at once: which Tick produced this Part, which `fn.*` Calculations ran, what they read, and — on click — the actual captured value (`wumpus/src/browser-workbench.js:21-34`; `wumpus/src/core/provenance.js:41-80`). It works because Wumpus captures values into the record at execution time rather than digesting them (`wumpus/src/core/execute.js:19-37`; `wumpus/src/core/pxc.js:26-69`), so every domain gets value-bearing receipts for free from `executeTick` itself. Its shortfalls are presentation, not architecture: one value per click, arrays truncated past 40 entries by `compact()`, browser-only — the TUI's `--inspect` panel is fed a snapshot that deletes exactly this material (`wumpus/src/session.js:26-29`).

**2. The ChainSpot neon correctness sheet, S1/S3, rows 3–4.** This is the only place a person literally *sees* the pixels the algorithm used — owned/muted/removed pixel sets, rejection buckets by color, and per-object identity crops painted onto the real canonical raster (`pyto/reference/chainspot-quick-anno/materialize_s3_neon.py:42-146`; `pyto/src/pyto/neon.py:32-158`). It is also the only view with recorded proof that visibility changed a finding: "Every one of these calls came from the per-object identity crop panels, and none of them is visible in the course-zoom panels that preceded them" (`DEV6_S3_SURVEY.md:172-175`) — a coarser view of the same computation hid what a finer one surfaced, which is the founding need stated as an experiment. It falls short on two axes: it is keyed by Stage, not Tick, so no Tick boundary inside a Stage is exposed to the viewer (`export_s3_snapshot.cjs:46-67`), and its cost is the highest of any repeatable view — a Node subprocess against a built `@chainspot/alg`, a sibling corpus checkout, and a second Python subprocess, per course per stage (`investigation.py:53-79`).

**3. `PCR.run(observe=True)` receipts joined to `PCR.mermaid()`, rows 25 and 27.** Together these are the only artifacts that carry the origin.md shape *as such*: the Mermaid output draws each Tick as a subgraph of its Calculations with Part-address edges labelled by argument name (`pyto/src/pyto/pcr.py:380-420`), and the Receipt records, per invocation, the frozen Calculation identity, declared-vs-actual consumes, the `writes` with their kind, and `shadowed_inputs` (`pcr.py:95-128,338-365`). This is the strongest *writer and reads* testimony in any runtime. It is third rather than first because it is value-blind by construction — `result_sha256` is a one-way digest (`pcr.py:125`) — it is dormant in practice (`pyto/reference/chainspot-quick-anno/s3.py:90` calls `pcr.run(pxc)` with `observe` defaulting to `False`), and the receipts dict is keyed by invocation id, not grouped by Tick, so even the Tick boundary must be re-derived from `testimony.json`.

## 3. What pyto's Python side lacks: a Tick materializer

Everything a per-Tick view needs is already computed and in memory at the end of `PCR.run`; nothing joins it, and nothing renders it. Concretely:

**Already present.**
- The Tick boundary and its Calculation order: `PcrRun.ticks` → `TickTestimony(name, calculations)` with each `CalculationTestimony(id, calculation, inputs, args, into)` (`pyto/src/pyto/pcr.py:63-146,371-378`).
- **The values.** `PCR.run` accumulates `results[invocation.id] = value` for every invocation and returns it as `PcrRun.results` (`pcr.py:296,332,378`). The actual computed Part value of every Calculation in every Tick is therefore live in the returned object — it is only ever digested on the way to a *file* (`result_sha256`, `pcr.py:125`; `retain.py:28`).
- Writer identity and reads: `Receipt.calculation` (`FrozenCalculation`, address + implementation sha256), `declared_consumes`/`actual_consumes`, `writes` (`PxWrite(address, kind)`), `shadowed_inputs` (`pcr.py:95-128,338-365`), populated whenever `observe=True`.
- The current store: `PxC.items()` returns every `(address, value)` pair sorted (`pyto/src/pyto/core.py:87-89`).
- Pixel rendering primitives: `dim`, `draw_boxes`, `paint_pixels`, `checkerboard`, `remaining`, `crops`, `panel`, `sheet` (`pyto/src/pyto/neon.py:32-181`), plus the stated house rule "neon first — if a panel needs pixel-peeping to tell whether the computation happened, the materialization failed" (`neon.py:1-6`).

**Missing, in the order a materializer needs it.**

1. **No function in `pyto/src/pyto/` consumes a `PcrRun`.** Grep for `materiali*` across `src/pyto/` matches only `neon.py:1-7`'s docstring — the kit was "promoted out of the S1 and S2 materializers" but no materializer came with it. Every actual materializer lives in an experiment tree and is hand-written per experiment (`pyto/reference/chainspot-quick-anno/materialize_s3_neon.py:42-146`; `pyto/experiments/grouped-ablation/run.py:292-293`). The gap is a `materialize_run(run: PcrRun, pxc: PxC) -> per-Tick panels` that closes over `run.ticks` (order and grouping), `run.results` (values), `run.receipts` (writer and reads), and `pxc` (post-run store).

2. **No Tick↔receipt join.** `PcrRun.receipts` is `dict[str, Receipt]` keyed by invocation id (`pcr.py:145`), and the only mapping from a Tick to its invocation ids is `TickTestimony.calculations[].id` (`pcr.py:143`). Any consumer must re-derive per-Tick grouping itself; the file layout on disk reproduces the split (`evidence/run-1/testimony.json` vs `receipts.json`).

3. **No value in any serialized form.** `Receipt` has no value field (`pcr.py:118-127`), `retained.json`'s `results` is documented and confirmed as `{invocation id: sha256|None}` (`retain.py:1-30`), and `PcrRun.ticks` is contractually frozen byte-identical with `observe` on or off (`pcr.py:130-140`) — so values cannot be added there without breaking that guarantee. The materializer needs its own output channel, not a widened receipt.

4. **No way to tell an image Part from a scalar Part.** `Part` carries an address and nothing else — "Identity is the address, not the current value" (`pyto/src/pyto/core.py:11-22`) — and `PxC` stores `dict[str, Any]` (`core.py:49`). There is no kind, dtype, or renderer tag, so a generic materializer has no basis on which to dispatch a Part to `neon.paint_pixels`/`neon.crops` rather than to `json.dumps`. Today that dispatch is hardcoded per stage in each experiment's materializer.

5. **No `Tick` object identity in the output.** `Tick` is a plain `name` + `calculations` list (`pcr.py:32-60`); `mermaid()` derives a node id by string-mangling the name (`pcr.py:404`). Nothing assigns a stable per-run Tick id that a panel file, an annotation, or a receipt could reference.

6. **No entry point.** `observe` defaults to `False` (`pcr.py:284`), there is no CLI or command that runs a PCR and writes a sheet, and the one reference investigation script neither passes `observe` (`s3.py:90`) nor calls the Mermaid writer it has available (`s3.py:72-90`; `investigation.py:87-97`, invoked only "when a graph is big enough that a human would rather look than read").

The concrete shape of what is absent: given `run = pcr.run(pxc, observe=True)`, emit one panel per `TickTestimony` — title = the Tick name; one row per `CalculationTestimony` carrying the writer (`receipt.calculation.address` + `implementation_sha256`), the reads (`receipt.declared_consumes` beside `receipt.actual_consumes`, so the divergence is visible rather than fatal), the `into` address, and the Part *as material*: `run.results[id]` rendered as text for scalars and through `neon.panel`/`neon.crops` for image Parts — composited by `neon.sheet` into one per-Tick sheet. Every input to that function exists today; only the function does not.

## 4. An agent-facing annotation surface: the LAB annotation grid convention

**The problem restated from the source.** `origin.md:10-12` records that toph "was awful: agents had to annotate, and the annotations carried no meaning," and `origin.md:14-17` records that the ABFeature engine produced "dumb receipts and self-verified." An annotation carries meaning when it is *addressed* — when it names the Tick, the Calculation, and the Part it is about, in the same identity scheme the execution used.

**Where the grid convention already exists.**
- `pyto/experiments/art-tournament/harness/contact_sheet.py:8-11`: `--grid` "draws a labelled coordinate overlay (in image pixels, spaced every N px) on top of every panel body so judges can reference exact positions when leaving notes, **matching the annotation-grid convention used elsewhere in the lab**." The implementation is `with_grid()` (`contact_sheet.py:23-40`): cyan gridlines at a fixed spacing with axis coordinate labels burned into the image, so a note can say *this* rather than gesture at the picture.
- The ChainSpot LAB original it matches: `./lab orient annotate`, "given a course name — generates a cropped raster + labeled coordinate grid for visual inspection of one course," implemented by `scripts/lab-grid.ts` (`lab-orient` SKILL.md:27-28, 202, at `/root/.claude/skills/synced/80361888-b704-4669-887a-108499ebf88c_d0a936e1-b1fb-4b59-b037-33bf79e2bde1/lab-orient/SKILL.md`). Note: `scripts/lab-grid.ts` and `scripts/chainspot-lab/orient.ts` do **not** exist in the read-only clone at `/home/user/samuelpmahan/chainspot/scripts/` — the convention is documented and mirrored in pyto, but its ChainSpot implementation is missing from what was made available.
- The same skill defines the annotation vocabulary the grid serves: "**Pixel evidence** — what's literally visible in the crop/grid" (SKILL.md:85), alongside gate/detector/invariant/case evidence.

**What the grid convention gets right, and what it stops short of.** It addresses a *pixel coordinate inside a rendered panel*. That is the finest-grained addressable annotation target anywhere in either runtime — and it is the wrong axis. It cannot say which Calculation painted the pixel, which Tick that Calculation belonged to, or which Part the pixel is a rendering of.

**What the agent-facing surface would be.** Extend the grid convention from image coordinates to Part identity, using ids the runtimes already assign:

- **Anchor.** `(pcr, tick.name, invocation.id, part.address)` — every component already exists and is already stable: `PcrRun.pcr` and `TickTestimony.name` (`pcr.py:63-146`), `CalculationTestimony.id` and `Receipt.invocation_id` (`pcr.py:113,143`), `Part.address` (`core.py:11-22`). The equivalent ids exist in DiscStudio's PQL composition (`src/core/exec.js:34-42`, Tick `name` + `call`/`with`/`into`), in ChessLab's receipts (`chesslab/src/lab/contract.ts:127-141`), and in Wumpus's records (`wumpus/src/core/execute.js:19-37`).
- **Grid, kept.** For image Parts, the annotation is `(anchor, x, y)` — the anchor names *what the picture is a picture of*, the `with_grid` overlay names *where in it* (`contact_sheet.py:23-40`). For scalar Parts the coordinate is simply omitted.
- **Verification vocabulary, kept.** The `lab-orient` evidence classes (SKILL.md:85) become the annotation's `kind`, so a note declares whether it rests on pixel evidence or on a gate/invariant claim.
- **Round-trip.** The annotation is written next to the Tick sheet the materializer of §3 emits, and read back by address — which is what makes it not a dumb receipt: the note and the trace share the identity scheme, so an agent that later re-runs the PCR can attach the prior annotation to the same Tick, the same Calculation, and the same Part, and detect that `implementation_sha256` (`pcr.py:90,347`) changed underneath it.

**Where the existing surfaces fall short of this, in code.** DiscStudio's review checklist keys comments to hand-authored feature ids (`'identity'`, `'bags'`, `'trace'`, …) plus a UI context snapshot, never a Tick name or `fn.*` address (`src/review-data.js:1-19`; `src/app.js:181`), while the one panel that *does* carry Tick names — "Inspect PQL composition" (`src/app.js:133`) — has no comment affordance at all. pyto's findings anchor to source line numbers (`'pcr.py:45'`) or whole evidence file paths (`pyto/experiments/runs/day1/verdicts/*.json`), never to an invocation id, although `testimony.json`, `mermaid.mmd` and `receipts.json` already assign exactly those ids. Net: today an agent has three disconnected ways to leave a note — a fixed checklist id, a source line, or an image pixel coordinate — and none of them says "this Tick's this Calculation wrote this Part."

## 5. The "slowest neural net" remark, read as a design statement

The owner's remark — "It could be the world's slowest neural net" — is recorded in `origin.md:29-31` with its own gloss: "Ticks as layers, Parts as named activations, receipts as the trace. The difference from a neural net is the point: every activation has a name a person chose, and every step is inspectable." Read as a design statement rather than a joke, it fixes the architecture's obligations term by term. *Ticks as layers* means a Tick is a synchronization boundary, not a convenience grouping: `origin.md:20-23` says a Tick is "where its Calculations become observable," and `PCR.run` honors this by executing every invocation in declaration order and emitting one `TickTestimony` per Tick (`pyto/src/pyto/pcr.py:284-378`) — the same discipline that makes a layer's outputs inspectable all at once. *Parts as named activations* means the address is the semantics: `Part` is documented as "a semantic PxC address. Identity is the address, not the current value" (`pyto/src/pyto/core.py:11-22`), so unlike a hidden unit whose meaning must be recovered post hoc by probing, a Part's meaning was declared by a person before anything ran, and is then composed by the Calculations that interpret it (`origin.md:18-19,39-41`). *Receipts as the trace* means every activation's provenance is recorded rather than reconstructed: the frozen Calculation identity, the declared-versus-actual reads, and the write kind (`pcr.py:95-128,338-365`), the analogue of a backward pass that reports what produced each value instead of how to change it. And the one property a neural net lacks is exactly the one the ledger above shows this system has not yet delivered either: not names, and not a trace, but **the activation's own value present at the layer where it was produced, visible to a person without writing code**. A neural net lacks it because its activations were never named; pyto lacks it because its serialized layers keep only digests — `Receipt.result_sha256` (`pcr.py:125`) and `retained.json`'s `{invocation id: sha256|None}` (`pyto/experiments/grouped-ablation/retain.py:28`) — even though `PCR.run` is holding every one of those values in `PcrRun.results` (`pcr.py:296,378`) at the moment the trace is written. The remark is therefore not a boast about slowness; it is a specification, and §3 is the one unbuilt piece of it.
